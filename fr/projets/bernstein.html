NOM

bernstein — déployer une application à cinq composants sur Kubernetes

SYNOPSIS

scripts/azure-infra.sh create|start|stop|destroy

scripts/deploy.sh azure|local

DESCRIPTION

Une application de vote (une page de vote en Python, un worker en Java, une page de résultats en Node.js, Redis et PostgreSQL) passe du code source à un cluster Kubernetes public sur Azure : construction des images, publication dans un registre privé, déploiement. Projet de 3e année, en binôme. C'est la même application que octopus(8), déployée cette fois sur un orchestrateur.

RÔLE

J'ai réalisé l'essentiel du dépôt : les manifestes Kubernetes, les scripts d'infrastructure Azure et de déploiement, les politiques réseau et le test de mise à jour sans coupure.

CONCEPTION

  • Kustomize plutôt que Helm. Les manifestes se lisent tels quels ; seuls les noms d'images changent entre Azure et le cluster local (kind).
  • Mises à jour sans coupure. Images taguées par commit Git, rolling update avec maxUnavailable: 0, hook preStop qui retire le pod du load balancer avant son arrêt, PodDisruptionBudgets. Un script interroge les deux pages pendant le déploiement et compte les erreurs : zéro.
  • Sondes. startup, readiness et liveness : un pod ne reçoit du trafic que lorsque ses dépendances répondent.
  • Disponibilité. Au moins deux réplicas des pages publiques, répartis sur les nœuds ; la page de vote passe de 2 à 5 réplicas selon le CPU.
  • Sécurité. Aucun secret dans le dépôt, Redis protégé par mot de passe, bases joignables seulement dans le cluster, NetworkPolicies entre pods, capacités Linux retirées, seccomp.
  • Coûts. Plan de contrôle AKS gratuit, et un script qui arrête les nœuds entre deux séances.
