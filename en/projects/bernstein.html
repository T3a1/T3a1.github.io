NAME

bernstein — deploy a five-component application on Kubernetes

SYNOPSIS

scripts/azure-infra.sh create|start|stop|destroy

scripts/deploy.sh azure|local

DESCRIPTION

A voting application (a Python voting page, a Java worker, a Node.js results page, Redis and PostgreSQL) goes from source code to a public Kubernetes cluster on Azure: building the images, pushing them to a private registry, deploying. A third-year pair project. It is the same application as octopus(8), this time on an orchestrator.

ROLE

I wrote most of the repository: the Kubernetes manifests, the Azure infrastructure and deployment scripts, the network policies and the zero-downtime test.

DESIGN

  • Kustomize rather than Helm. The manifests read as they are; only the image names change between Azure and the local cluster (kind).
  • Zero-downtime updates. Images tagged with the Git commit, rolling updates with maxUnavailable: 0, a preStop hook that takes the pod out of the load balancer before it stops, PodDisruptionBudgets. A script polls both pages during a deployment and counts errors: zero.
  • Probes. Startup, readiness and liveness: a pod only gets traffic once its dependencies answer.
  • Availability. At least two replicas of each public page, spread over the nodes; the voting page scales from 2 to 5 replicas on CPU.
  • Security. No secret in the repository, password-protected Redis, databases reachable only inside the cluster, NetworkPolicies between pods, dropped Linux capabilities, seccomp.
  • Cost. Free AKS control plane, and a script that stops the nodes between sessions.
